# Translation Handoff (ar / he / fa / hr)

**Status:** open, decision-gated. Nothing in this document was translated by a
machine, and nothing here is a code defect. It is the list of strings a human
translator still has to author, in the shape they need it, plus the Croatian
(`hr`) availability question this release must not answer by guessing.

Owner of the work: a translator with product context (legal, intelligence and
safety wording). Owner of the plumbing: engineering, via
`tools/i18n/export_translation_gaps.py`.

---

## 1. Why this is a handoff and not a fix

`tests/integration/test_translation_coverage.py::test_no_catalog_entry_is_empty_or_fuzzy`
requires **every** entry in `ar`, `he`, `fa` and `hr` to be translated and
non-fuzzy. It is a 100% gate, not a percentage threshold: 3 400 correct entries
do not compensate for one empty one.

Filling those entries automatically would turn four red tests green and degrade
the product in the one place where a wrong word has consequences — a legal
notice, an intelligence caveat, a delete confirmation. The repository rule is
therefore: **no machine-filled translations, ever**. The gap is exported, the
translator decides, engineering applies and recompiles.

Two axes are measured, and they are different:

| axis | meaning | where it is caught |
| --- | --- | --- |
| missing `msgid` | a string used in a template or script that the catalogue does not contain at all | `test_the_interface_templates_have_strings_to_check`, `test_every_interface_string_is_translated` |
| empty / fuzzy entry | the `msgid` is in the catalogue, but `msgstr` is blank or marked `#, fuzzy` | `test_no_catalog_entry_is_empty_or_fuzzy` |

The second axis is the 1 236-entry gap below. The first is closed (0 missing
interface strings, checked by `python tools/audit/check_structure.py`).

Columns: `msgid`, `msgid_plural` (only for plural entries), `status`
(`missing` / `fuzzy` / `partial`), `module`, `current_draft` (the existing but
untrusted string — present only for `fuzzy`/`partial`, never for `missing`),
`translation` (**always empty, by construction**), `sources` (`path:line`).

The `translation` column is the only column a translator writes. The exporter
does not read it back; applying a filled sheet is a separate, reviewed step.

## 3. Workflow

1. **Export** (engineering, or the translator locally):
   `python tools/i18n/export_translation_gaps.py`
2. **Translate** the `translation` column of one worksheet. Leave `msgid`,
   `status`, `module`, `current_draft`, `sources` untouched.
   Placeholders (`%(name)s`, `{count}`, `%s`) and HTML entities must survive
   verbatim — `test_placeholder_layout_survives_translation` enforces the layout
   signature after the fact.
3. **Apply** into `translations/<lang>/LC_MESSAGES/messages.po` **in place**
   (append/replace the `msgstr` lines; do not rewrite the catalogue through a
   serializer, and never use `pybabel update --previous`: both have already
   corrupted unrelated msgids in this project). Clear the `#, fuzzy` flag on
   entries that were reviewed.
4. **Recompile**: `pybabel compile -d translations -l <lang>` (or
   `python -m babel.messages.frontend compile -i <po> -o <mo>`).
5. **Verify**:
   - `pytest tests/integration/test_translation_coverage.py -q` → the
     `test_no_catalog_entry_is_empty_or_fuzzy[<lang>]` case must pass;
   - `pytest tests/integration/test_analyst_i18n.py -q` (`.mo` freshness, RTL
     rendering, `hr` registry pin);
   - `python tools/audit/check_structure.py` (0 incomplete msgid catalogs).
6. **Regenerate the worksheets in the same commit**
   (`python tools/i18n/export_translation_gaps.py`), so the committed sheets and
   the catalogues never disagree. `python tools/i18n/export_translation_gaps.py
   --check` is enforced by `tests/unit/test_translation_gap_export.py`.

A partial handback is a commit, not a failure: the gate stays red until the last
entry lands, and the worksheets shrink with each commit. That is the intended
signal.

## 4. Croatian (`hr`) decision brief

### What is true today (all pinned by tests, all verified)

| fact | evidence |
| --- | --- |
| `hr` is **not** in the UI language registry | `settings/languages.py` → `SUPPORTED_LANGUAGES` = `en, ar, he, fa`; pinned by `tests/integration/test_analyst_i18n.py::test_hr_catalog_is_maintained_but_not_exposed` |
| the app's language list is derived from that registry, not duplicated | `apps/web/app.py:119` → `app.config['LANGUAGES'] = dict(SUPPORTED_LANGUAGES)`; `settings/routes.py` and `Api/routes/common.py` read `config['LANGUAGES']` |
| admins cannot edit `hr` in the Translation Manager | `Api/services/translation_management.py::supported_translation_languages()` filters `SUPPORTED_LANGUAGES`; pinned by `tests/unit/test_translation_management_service.py::test_only_canonical_target_languages_are_editable` (asserts `{'ar','he','fa'}` and `validate_translation_locale('hr') is False`) |
| the `hr` catalogue still exists, compiled, and is kept in sync | `translations/hr/LC_MESSAGES/messages.{po,mo}` (4 104 entries, 90.28 % of the POT, 359 gap); `test_hr_catalog_is_maintained_but_not_exposed` asserts every tracked new msgid is present |
| the coverage gate counts `hr` | `tests/integration/test_translation_coverage.py` → `MAINTAINED = ('ar','he','fa','hr')` |
| there is **no** client locale pack for `hr` | `static/js/i18n/locales/` holds `ar.js, en.js, fa.js, he.js`; `test_the_packs_offer_the_same_languages_as_the_application` requires a pack per offered language |
| `hr` is Latin-script LTR | no `dir="rtl"` handling applies (`RTL_LANGUAGES` = `ar, he, fa, ur`) |

So the product maintains a language it cannot show. That is a deliberate,
test-pinned ambiguity inherited from the catalogue seeding, and it is the only
localization question this release cannot settle on evidence: it is a product
decision about a market, not an engineering defect.

### Option A — keep `hr` excluded, documented (status quo, zero code change)

- **Change:** nothing in code; this document is the record. Optionally add one
  sentence to the user-facing release notes ("Croatian ships as a maintained
  catalogue, not as a selectable language").
- **Cost:** zero engineering, zero risk. The 359 `hr` entries stay in the
  translator handoff and keep one integration gate red.
- **Consequence:** a Croatian user sees the English interface, with no hint that
  a 90 % catalogue exists. Nothing breaks; nothing is promised.
- **Verdict:** safe default. Correct if there is no committed Croatian market.

### Option B — enable `hr` in the UI and in the Translation Manager

- **Change (6 places, all small but all required):**
  1. `settings/languages.py`: add `('hr', 'Hrvatski')` to `SUPPORTED_LANGUAGES`
     (this automatically feeds `app.config['LANGUAGES']`, the sidebar switcher,
     the Settings selector, `/set_language/<code>` and the Translation Manager
     target list).
  2. `settings/settings_models.py:602`: the `ImportError` fallback copy of the
     registry repeats the four codes and drives `system.language`'
     `allowed_values`; it must gain `hr` too, or validation on a host where the
     registry import fails would reject the new value.
  3. `static/js/i18n/locales/hr.js`: a client pack **must** be authored and
     registered (`test_the_packs_offer_the_same_languages_as_the_application`
     fails without it, and the JS-rendered pages would fall back to English
     silently).
  4. Complete the `hr` catalogue: **359 entries** (80 missing, 279 fuzzy) — this
     is the same translator handoff, now on the release critical path.
  5. Flip three tests that pin the exclusion:
     `test_hr_catalog_is_maintained_but_not_exposed` (becomes "hr is exposed"),
     `test_only_canonical_target_languages_are_editable` (`{'ar','he','fa','hr'}`,
     `validate_translation_locale('hr') is True`), and `MAINTAINED`/`OFFERED`
     in `test_translation_coverage.py` (add `hr` to `OFFERED`; the rendered-page
     assertions then run for `hr` too).
  6. Re-run the full i18n integration surface: pack/catalogue agreement,
     rendered-page assertions for the now-`hr` pages, and
     `tools/audit/check_structure.py`.
- **Cost:** the 359 translations (the dominant cost), one client pack, ~6 file
  changes plus test updates. No database or migration change.
- **Consequence:** Croatian becomes a supported language with a translation
  workflow; any gap is then user-visible, so the gate becomes release-blocking
  rather than informational.
- **Verdict:** the right option if Croatian is a target market. Not something
  this stage may assume.

### Option C — keep `hr` out of the UI, but make that explicit configuration

- **Change:** add a setting (e.g. `TRANSLATION_MAINTAINED_LOCALES` or
  `hr.enabled = false`) that declares "translated and exported, not offered",
  and have `supported_translation_languages()` / the Translation Manager read it
  so an operator can turn `hr` on for editing without offering it in the
  switcher. Add `hr` to `babel.cfg`-independent validation lists accordingly, and
  one test per state.
- **Cost:** ~2 days of design and tests (a new configuration surface, default
  behaviour, admin UI affordance, docs); the 359 translations remain a handoff
  but can now be entered through the product instead of a CSV round trip.
- **Consequence:** the ambiguity becomes an explicit, documented switch — but
  also a new configuration surface with two states to test, and a half-offered
  language is a support question ("why can my admin see Croatian and I cannot?").
- **Verdict:** only worth it if the team expects more maintained-but-unoffered
  locales, or wants translators to work inside the Translation Manager. For one
  locale, it is more machinery than the problem.

### What is required from the decision owner

Pick **A**, **B** or **C** — or "A now, B after the Croatian translations land".
Until then this release ships **A** and says so. Nothing in this stage
pre-commits the choice: no `hr` entry was added to the registry, no test that
pins the exclusion was edited, and no `hr` string was translated.

## 5. What engineering already guarantees while the handoff is open

- Every string the interface uses exists in the POT and in all four catalogues
  (0 missing msgids, `tools/audit/check_structure.py`).
- `.mo` files are compiled and current (`test_mo_files_are_compiled_with_new_msgids`).
- Placeholder layout survives translation (`test_placeholder_layout_survives_translation`).
- Client packs and catalogues agree where both carry a string
  (`test_pack_and_catalog_agree_where_both_have_a_string`).
- The handoff cannot rot: `tests/unit/test_translation_gap_export.py` fails if the
  committed worksheets stop matching the catalogues.
- No tool in this repository writes into `translations/` except an explicit,
  reviewed apply step; the exporter is tested to leave the catalogues
  byte-identical.
